# Decision Packet — 跨线程投递的目标解析政策

> 给 operator 的**价值取舍题**，不是技术 A/B 题。
> 证据见同目录 `README.md`（6 个事件 / 11 条 thread / 2026-04-30 → 2026-09-19）。

## 已经不用你决定的部分

- 服务端 continuation 绑错 thread：**已证伪**（0/7755 因果边、0/663 session 绑定）。不需要修。
- 接收侧 provenance 被截成常量 `thread_m`：**已确认是 bug，已在同 PR 修**。不需要你决定。
- skill 里那条悬空的"P2 OPEN 服务端 bug"断言：**已修正**。不需要你决定。
- 「加个**内容启发式** guard 拦掉不相关 target」：**已量化否掉**——两个最自然的 fence
  （发送方无历史发言 / subject 在目标 thread 未出现）对本 corpus 的误投**拦不住**，
  而它们的**拒绝比例**高达 7%~50%（= 会拒掉这么多真实跨投流量）。我不建议做，也不打算做。
  （两句限定语都很重要：① 否掉的是**内容启发式**这一类，**结构性 standing 判据是另一类**，
  见取舍 2；② 语料**没有 per-delivery 标注**，所以全文所有百分比都是**拒绝比例**，
  不是"误杀率"——被拒的里面有多少本来是对的，这个库里没有证据能回答。）

## 需要你决定的部分

真正的根因是：**`cross_post_message` 要求猫提供一个它结构上无法核验的坐标**。
猫要找的是「F167 的 owner thread」「我的平行实例」「跟本 thread 关联的 thread」——
都是**角色**，不是 id；系统既不提供解析原语，也不提供"我不知道 id"的合法出口。
于是猫只能猜一个最近见过的 threadId，猜错了没人发现，只有你发现。

这块要花代价，代价花在哪由你定。

> ⚠️ **B 的账要拆成三段：发现 / 纠正 / 阻断**
> （初稿写过头；二稿把 quarantine 算进 B；三稿把"首次发现"算进 typed 标记；
> 四稿又把一条**真预防**原语打包进 B-1。这是第五稿——四次都是同一个病：
> **把不同机制的收益记在同一个购买决定名下**。所以下面每一段都写清楚"谁买单、买到什么"。）：
>
> - **"误投 → 被发现"**：**三个变体在这一段上不同价，别一起记。**
>   **B-1 不改善**——事后标记以"已经有人发现"为起点，而今天没有任何自动检测器
>   （R-5：6 次事件全部由人类发现，I-1 延迟 23 分钟）。
>   **B-2 也不是检测器**——它不判别任何东西，只是把所有投递挡在唤醒之前，
>   等于强制全员前置审阅；发现的仍然是人，只是被迫提前到消费前。
>   **只有 B-3 真的带一个检测面**：classifier / grounding 判据会在投递时标出可疑投递，
>   这正是今天完全不存在的东西。但它的 precision 今天**无法评估**（语料无 per-delivery 标注），
>   所以"能把这 23 分钟压到多少"**我给不出数**——这也正是 B-1 的标注数据值钱的地方。
> - **"发现 → 完成纠正"**：只要有 typed 误投信号 + 反向唤醒就成立，**不依赖任何判据**。
>   这是 B-1 唯一真买到的东西。
> - **"不产生二次污染"**：**在 quarantine 三选一里，只有在接收猫消费之前生效才成立。**
>   （**唯一例外不在这三选一里**：取舍 1b 的"回复方向由服务端推导"确实是预防，
>   但它只消灭 I-1b 那一类，见下一节——我把它拆出去单独问，就是为了不让 B-1 借它的光。）
>   一旦消息已经唤醒了接收猫，事后标记**追不回**已经读进上下文的内容，也**撤不回**它已经发出去的
>   二次投递——I-1b 距 I-1 只有 112 秒，而 operator 是在 23 分钟后才发现的。在那个窗口里，
>   任何"事后"机制都已经晚了。
>
> **二稿的错在这里**：它一边说 B"不依赖任何判据"，一边把 pre-consumption quarantine 算进 B 的收益。
> 这两件事不能同时为真——**要在消费前隔离，就必须先知道隔离谁**，而你的 typed 标记发生在**发现之后**。
> **三稿的错在隔壁**：它承认了上面这条，却还在表格外面写"把发现时间从 23 分钟压到秒级"。
> 同一条不变量管着两处——**发生在发现之后的机制，既挡不住已成的污染，也缩不短发现本身**。
> 所以 quarantine 不是 B 的一个勾选项，它本身是一道**三选一**，且每一项都有明码标价：
>
> | quarantine 变体 | 触发靠什么 | 真实收益 | 真实代价 |
> |---|---|---|---|
> | **B-1 事后标记**（纯 fail-loud） | operator 或猫**发现之后**打标 | 只买"发现→完成纠正"这一段：I-1 里这一段耗时 **3 分 44 秒（13:14:09→13:17:53）、产出 4 条纠正/撤回消息**，且 referent 还选错了；B-1 把它换成一次点选 + 一次结构化反向唤醒。附带留下**今天完全不存在的误投标注**。**不缩短首次发现时间，不阻止已成污染** | 几乎为零 |
> | **B-2 全量先隔离** | 不需要判据：**所有** cross-post 一律先不唤醒，等确认 | 真能阻止二次污染 | **每一条跨投都要付确认延迟**，含全部正常协作 |
> | **B-3 选择性隔离** | 需要 classifier / grounding 判据 | 只隔离可疑的 | **不能再声称"不依赖判据"**，且判据的 precision 我们今天没有（见 R-2b） |
>
> 请按变体分别验收，别拿 B-1 的成本去买 B-2/B-3 的收益。

**我的立场**：选 B，且**只买 B-1**。理由只有一条，而且**不是"阻断污染"**：
B-1 以接近零的成本换掉"发现之后"那一段——I-1 里那 3 分 44 秒、4 条纠正/撤回、
一次选错的 referent（MAIN 前 20 分钟收了 6 条 cross-post，"刚投错的那条"至少有 7 个候选，见 R-5），
全部由一次点选 + 一次结构化反向唤醒取代，且不给任何正常协作加延迟。

**二次污染（I-1b、I-2b）要真阻断，只有 B-2 或 B-3，我两个都不建议现在买**：
B-2 要全部正常协作陪付确认延迟；B-3 需要一个判据，而"判据 precision 未知"恰恰是因为
我们今天**一条误投标注都没有**（见取舍 2 / R-2b）。这两件事连起来，B-1 的第二个价值才浮出来：
**它是 B-3 与取舍 2 fail-closed 路线唯一便宜的前置条件**——先攒标注，再谈按判据拦谁。

**唯一的预防例外我拆到了取舍 1b**：服务端推导回复方向那条原语**确实预防**，
但它只消灭 I-1b 那一类。四稿把它算在 B-1 名下，于是 B-1 同时声称"不买预防"和"消灭 I-1b"，
两句不能同时为真。现在它是一道独立的题。

### 取舍 1b：要不要让服务端推导「回复源 thread」的 target？（**独立于 quarantine 三选一**）

这条前四稿一直写在 B 里面，是错的——**它不是 quarantine 的第四个变体**。
quarantine 三选一决定的是"一条可能投错的消息要不要先拦住"；这条原语**不做那个判断**，
它消掉的是**一个猜 id 的位点**：被 cross-post 唤醒时，源 thread 已经记在
`extra.crossPost.sourceThreadId` 里；`replyTo` 又已经被服务端约束在目标 thread 内
（`resolveVisibleReplyParent`）。也就是说"回复源 thread"这个动作
**完全不需要猫再打一次 threadId**。

**所以要挑明：这条原语确实是预防，B-1 不是。** 它在误投发生前就消灭一整类。
但它的预防面**极窄，且边界是结构可判定的**，不是启发式——逐行对 §2 corpus 验过：

| corpus 行 | 覆盖？ | 为什么 |
|---|---|---|
| **I-1b** | ✅ **消灭** | 被唤醒的 opus 要回的就是源 thread，却重新猜了一个 id，投给第三条无关 thread（C1-Plugins）。服务端直接给出源 thread，无从猜起 |
| **I-2b** | ❌ | codex 那条**投到的恰恰就是源 thread**（`thread_ms2kxwwny5z5fcom`），target 一个字没错——错在它同一个 turn 里**已经就地正确回复过了，本不该再发第二条**。自动推导只会得到同一个目标。这一类要的是 **no-op / ACK suppression**（"只需阅读知悉时不产生新投递"），是另一个能力 |
| **I-1 / I-2a / I-3 / I-4 / I-5** | ❌ | 这五行全是**主动发起**投递时方向就选错，不是"回复"——没有源 thread 可推导。它们要的是取舍 2 的解析原语 |

**账这么记**：§2 corpus 那 7 行里它消灭 **1 行（I-1b）**，代价是**零判据、零延迟、零误杀**——
源 thread 是服务端**已记录的事实**，不是推断；它只是把这个事实做成一个可直接用的 target，
**不剥夺猫显式指定别的 target 的能力**，所以不存在拦错正常协作的可能。
**但它不是"阻断二次污染"的完整答案**——完整答案仍然只有 B-2 / B-3。

**我的立场**：做。它与取舍 1 的选择**正交**，可以和 B-1 一起做，也可以单独做；
它是本 packet 里唯一一条**零判据的预防**。

### 取舍 2：要不要给「角色 → thread」建一个真相源？

I-4 里你亲口给出过正确不变量：**"我们 thread 当前应该有且只和 `thread_mrkn6povq4zzgh45` 有关联的"**。
这句话是对的、是稳定的、而系统里**没有任何地方能存这种"任意关联"**——
它不是父子血缘（父子血缘是有地方存的，见下），而是一句**排他性**声明（"有且只和 X"）。
`parentThreadId` 既表达不了"任意两条 thread 相关"，也表达不了"除此之外都不相关"。

核查（2026-09-19 只读实测，§2 涉事的 **11 条 thread 逐条查完，无抽样**）：
`cat-cafe:thread:*` 的 `metadata` / `labels` **11/11 全空**，`parentThreadId` **只有 1 条有**
（`thread_mrrucuwlotamwuom` → `thread_mrdip0u5aw4ysi97`，正是 I-3 那条）。
`cat_cafe_get_thread_metadata` 这个能力存在，但实际上没人填。

**补测（两轮，第二轮直接改变了这题的答案）**：系统里其实**已经有半个真相源**——
`RedisThreadStore` 持久化 `parentThreadId` 并维护 children 索引。全量实测：

- 531 条 thread 里只有 **29 条（5.5%）**声明了 `parentThreadId`——这是**父链接填充率**（图有多稀疏），
  **不是"多少投递有 standing"**；后者这个库里没有字段能回答，是未知量；
- 一刀切按血缘 fail-closed 的**拒绝比例**是 **74.6%**（比内容 fence 更差，否决）；
- **上一稿到这里下了"有界、可评估"的结论，本轮撤回**：那一稿只统计了"源 thread 自己声明了父"
  这个**最窄 scope**（139/960 = 14.5% 适用面，18.7% 拒绝比例）。但一条 thread**自己就是别人的父**
  （children 索引）同样是已记录的血缘。把两种形态都算上：适用面 **69.9%**，
  拒绝比例 **63.6%**。"有界的 18.7%" 是 scope 选窄了的假象；
- 而且两个数字**都只是拒绝比例，不是误杀率**——语料无标注，26 条里已知**至少一条是真阳性**
  （I-3），其余既不能算对也不能算错；
- **I-3 仍然是决定性样本，也是唯一一个已确认的真阳性**：源 thread `thread_mrrucuwlotamwuom` 的
  `parentThreadId` 正是 `thread_mrdip0u5aw4ysi97`，也就是**你当时口头指出的正确目标**。
  出错那一刻，正确答案已经躺在服务端的 thread store 里，猫却在猜。

**结论因此分成两半，别混着记账**：

- **"把已有血缘呈现给猫"（advisory）**：立刻能做，不依赖父链接填充率、不依赖标注，
  I-3 直接证明它有效——成本是几行读取。
- **"据此拒绝投递"（fail-closed）**：**今天不成立**。三个缺口：图稀疏（父链接填充率 5.5%）、precision 未知、
  且血缘是**开放世界**（族外 ≠ 无依据——Core↔Plugins 这种正常跨 feature 协作本来就没有血缘边）。
  要走这条路，前提是先有标注样本，或一份**显式、排他**的关联契约（就是你在 I-4 说的那句话）。

| | **A. 不建** | **B. 轻量：thread 关联表** | **C. 重量：feature/subject → owner thread 注册表** |
|---|---|---|---|
| 做法 | 维持现状，靠猫每次 `feat_index` + 查证 | 每条 thread 声明它的关联 thread（你在 I-4 说的那句话直接落库，**含"有且只和"这层排他性**），cross-post 到关联集合外时在消息上打**可见的 provenance 标记**（不拦） | F-号 / subject 有唯一 owner thread；`cross_post_message` 支持 `subjectRef` 直接解析 target，猫不再传 id |
| 你付出什么 | 继续当人肉路由器 | 每条新 thread 多一次声明（可由猫提议、你批） | 需要一套注册 + 争用 + 迁移语义；I-1/I-2a 的根源「F167 压根没有 owner thread」也需要一个"无 owner"的合法状态 |
| 收益 | 0 | 覆盖 I-4，部分覆盖 I-1 | 覆盖 I-1 / I-2a / I-3（平行实例可解析），根治 R-1 |
| 我的倾向 | ❌ | ✅ 值得做，成本低 | 想做，但**不建议现在做** —— 它需要先有 B 的数据说明"角色解析"到底多频繁 |

**我的立场**：B 现在做，C 记进 backlog 等数据。
