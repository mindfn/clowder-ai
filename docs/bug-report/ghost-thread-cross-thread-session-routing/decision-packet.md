## 已经不用你决定的部分

- 接收侧 provenance 被截成常量 `thread_m`：**已确认是 bug，已在同 PR 修**。不需要你决定。

- 「加个**内容启发式** guard 拦掉不相关 target」：**已量化否掉**——两个最自然的 fence
  （发送方无历史发言 / subject 在目标 thread 未出现）对本 corpus 的误投**拦不住**，
  而它们的**拒绝比例**高达 7%~50%（= 会拒掉这么多真实跨投流量）。我不建议做，也不打算做。
  （两句限定语都很重要：① 否掉的是**内容启发式**这一类，**结构性 standing 判据是另一类**，
  见取舍 2；② 语料**没有 per-delivery 标注**，所以全文所有百分比都是**拒绝比例**，
  不是"误杀率"——被拒的里面有多少本来是对的，这个库里没有证据能回答。）

## 需要你决定的部分

真正的根因是：**`cross_post_message` 要求猫提供一个它结构上无法核验的坐标**。
猫要找的是「F167 的 owner thread」「我的平行实例」「跟本 thread 关联的 thread」——
都是**角色**，不是 id；系统既不提供解析原语，也不提供"我不知道 id"的合法出口。
于是猫只能猜一个最近见过的 threadId，猜错了没人发现，只有你发现。

这块要花代价，代价花在哪由你定。

### 取舍 1：猫投错了，应该拦、还是应该可回收？

| | **A. 事前拦（fail-closed）** | **B. 事后可回收（fail-loud）** | **C. 两者都要** |
|---|---|---|---|
| 做法 | 目标 thread 与本次 subject 无任何可核验关联时，`cross_post_message` 返回 400，要求补一个 typed `targetGrounding`（形状照抄已有的 `groundingEvidenceRef`），或改走 `propose_thread` | 投递照常，但增加 ①「这条投递错了」的 typed 信号（你一键、猫也能自查）+ ③ 发送方被反向唤醒纠正。**② quarantine 是一个独立的、必须单独选的子问题，见下方 ⚠️** | 先 B 后 A |
| 你得到什么 | 误投在发生前就被挡住 | 误投仍会发生。**目标**是把发现时间从 23 分钟压到秒级、并把二次污染链掐断——但这两件事的达成条件不同，见下方 ⚠️ | — |
| 你付出什么 | **首次跨 feature 协作会被拦下**。R-2 的数据说历史真实流量里有 7.3% 的 cross-post 是冷启动首次接触（语料无标注，不代表这 7.3% 都是对的，但它们今天确实都发出去了）；这些会变成"先补 grounding 再发" | 误投照旧发生，你仍然是第一发现人（但只需点一下，不需要打字解释） | 工期最长 |
| 我的倾向 | ✋ 不建议单独做 A —— 没有可用判据，只能靠猫自陈 grounding，等于再写一条"规则"，而 F167 Case E1 已经证明「写进规则 ≠ 模型执行」 | ✅ **推荐先做 B** —— 它不依赖任何判据，只依赖"错了之后能不能收回来" | 可以，但 A 应该等 B 跑出真实数据再谈 |

> ⚠️ **B 的两个收益不是同一个东西，别一起记账**（初稿写过头了，二稿仍有一处因果错，这是第三稿）：
>
> - **"发现时间 → 秒级"**：只要有 typed 误投信号就成立，**不依赖任何判据**。
> - **"不产生二次污染"**：**只有 quarantine 在接收猫消费之前生效才成立。**
>   一旦消息已经唤醒了接收猫，事后标记**追不回**已经读进上下文的内容，也**撤不回**它已经发出去的
>   二次投递——I-1b 距 I-1 只有 112 秒，而 operator 是在 23 分钟后才发现的。在那个窗口里，
>   任何"事后"机制都已经晚了。
>
> **二稿的错在这里**：它一边说 B"不依赖任何判据"，一边把 pre-consumption quarantine 算进 B 的收益。
> 这两件事不能同时为真——**要在消费前隔离，就必须先知道隔离谁**，而你的 typed 标记发生在**发现之后**。
> 所以 quarantine 不是 B 的一个勾选项，它本身是一道**三选一**，且每一项都有明码标价：
>
> | quarantine 变体 | 触发靠什么 | 真实收益 | 真实代价 |
> |---|---|---|---|
> | **B-1 事后标记**（纯 fail-loud） | operator 或猫**发现之后**打标 | 纠正成本↓、审计留痕。**不缩短首次发现时间，不阻止已成污染** | 几乎为零 |
> | **B-2 全量先隔离** | 不需要判据：**所有** cross-post 一律先不唤醒，等确认 | 真能阻止二次污染 | **每一条跨投都要付确认延迟**，含全部正常协作 |
> | **B-3 选择性隔离** | 需要 classifier / grounding 判据 | 只隔离可疑的 | **不能再声称"不依赖判据"**，且判据的 precision 我们今天没有（见 R-2b） |
>
> 请按变体分别验收，别拿 B-1 的成本去买 B-2/B-3 的收益。

**我的立场**：选 B。理由是 corpus 里 6 个事件的真实伤害不在"投错了"这一下，
而在**投错之后没人知道、错的那条 thread 的猫还继续基于错的语境做二次协调**（I-1b、I-2b 两次都这样）。
止住二次污染比阻止首次误投便宜得多，而且（在 B-1 形态下）不给任何正常协作加延迟。

**B 里有一块几乎零争议、我特别想要的**：**回复方向的 target 可以由服务端推导，不用猫填。**
被 cross-post 唤醒时，源 thread 已经记在 `extra.crossPost.sourceThreadId` 里；
`replyTo` 又已经被服务端约束在目标 thread 内（`resolveVisibleReplyParent`）。
也就是说"回复源 thread"这个动作**完全不需要猫再打一次 threadId**。
**它能覆盖的是 I-1b，不是 I-2b——这两条必须分开记账**：

- **I-1b（覆盖）**：被唤醒的 opus 要回的是源 thread，却重新猜了一个 id，投给了第三条无关 thread
  （C1-Plugins）。服务端推导源 thread 直接消灭这一类。
- **I-2b（不覆盖）**：codex 那条**投到的恰恰就是源 thread**（`thread_ms2kxwwny5z5fcom`），
  target 一个字都没错——错在它同一个 turn 里**已经就地正确回复过了，本不该再发第二条**。
  自动推导源 thread 只会得到同一个目标，拦不住它。这一类要的是 **no-op / ACK suppression**
  （"只需阅读知悉时不产生新投递"），是另一个能力。

所以这条原语的账要这么记：**消灭 I-1b 这一类（回复方向猜 id），不需要任何启发式判断；
I-2b 那一类不在它的收益里。**

### 取舍 2：要不要给「角色 → thread」建一个真相源？

I-4 里你亲口给出过正确不变量：**"我们 thread 当前应该有且只和 `thread_mrkn6povq4zzgh45` 有关联的"**。
这句话是对的、是稳定的、而系统里**没有任何地方能存这种"任意关联"**——
它不是父子血缘（父子血缘是有地方存的，见下），而是一句**排他性**声明（"有且只和 X"）。
`parentThreadId` 既表达不了"任意两条 thread 相关"，也表达不了"除此之外都不相关"。

核查（2026-09-19 只读实测，§2 涉事的 **11 条 thread 逐条查完，无抽样**）：
`cat-cafe:thread:*` 的 `metadata` / `labels` **11/11 全空**，`parentThreadId` **只有 1 条有**
（`thread_mrrucuwlotamwuom` → `thread_mrdip0u5aw4ysi97`，正是 I-3 那条）。
`cat_cafe_get_thread_metadata` 这个能力存在，但实际上没人填。

**补测（两轮，第二轮直接改变了这题的答案）**：系统里其实**已经有半个真相源**——
`RedisThreadStore` 持久化 `parentThreadId` 并维护 children 索引。全量实测：

- 531 条 thread 里只有 **29 条（5.5%）**声明了 `parentThreadId`——这是**父链接填充率**（图有多稀疏），
  **不是"多少投递有 standing"**；后者这个库里没有字段能回答，是未知量；
- 一刀切按血缘 fail-closed 的**拒绝比例**是 **74.6%**（比内容 fence 更差，否决）；
- **上一稿到这里下了"有界、可评估"的结论，本轮撤回**：那一稿只统计了"源 thread 自己声明了父"
  这个**最窄 scope**（139/960 = 14.5% 适用面，18.7% 拒绝比例）。但一条 thread**自己就是别人的父**
  （children 索引）同样是已记录的血缘。把两种形态都算上：适用面 **69.9%**，
  拒绝比例 **63.6%**。"有界的 18.7%" 是 scope 选窄了的假象；
- 而且两个数字**都只是拒绝比例，不是误杀率**——语料无标注，26 条里已知**至少一条是真阳性**
  （I-3），其余既不能算对也不能算错；
- **I-3 仍然是决定性样本，也是唯一一个已确认的真阳性**：源 thread `thread_mrrucuwlotamwuom` 的
  `parentThreadId` 正是 `thread_mrdip0u5aw4ysi97`，也就是**你当时口头指出的正确目标**。
  出错那一刻，正确答案已经躺在服务端的 thread store 里，猫却在猜。

**结论因此分成两半，别混着记账**：

- **"把已有血缘呈现给猫"（advisory）**：立刻能做，不依赖覆盖率、不依赖标注，
  I-3 直接证明它有效——成本是几行读取。
- **"据此拒绝投递"（fail-closed）**：**今天不成立**。三个缺口：图稀疏（父链接填充率 5.5%）、precision 未知、
  且血缘是**开放世界**（族外 ≠ 无依据——Core↔Plugins 这种正常跨 feature 协作本来就没有血缘边）。
  要走这条路，前提是先有标注样本，或一份**显式、排他**的关联契约（就是你在 I-4 说的那句话）。

| | **A. 不建** | **B. 轻量：thread 关联表** | **C. 重量：feature/subject → owner thread 注册表** |
|---|---|---|---|
| 做法 | 维持现状，靠猫每次 `feat_index` + 查证 | 每条 thread 声明它的关联 thread（你在 I-4 说的那句话直接落库，**含"有且只和"这层排他性**），cross-post 到关联集合外时在消息上打**可见的 provenance 标记**（不拦） | F-号 / subject 有唯一 owner thread；`cross_post_message` 支持 `subjectRef` 直接解析 target，猫不再传 id |
| 你付出什么 | 继续当人肉路由器 | 每条新 thread 多一次声明（可由猫提议、你批） | 需要一套注册 + 争用 + 迁移语义；I-1/I-2a 的根源「F167 压根没有 owner thread」也需要一个"无 owner"的合法状态 |
| 收益 | 0 | 覆盖 I-4，部分覆盖 I-1 | 覆盖 I-1 / I-2a / I-3（平行实例可解析），根治 R-1 |
| 我的倾向 | ❌ | ✅ 值得做，成本低 | 想做，但**不建议现在做** —— 它需要先有 B 的数据说明"角色解析"到底多频繁 |

**我的立场**：B 现在做，C 记进 backlog 等数据。
