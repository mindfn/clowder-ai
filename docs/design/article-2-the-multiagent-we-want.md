# 我们期望中的 Multi-Agent 是怎样的

上一篇我们说，multi-agent 的关键是拆开了什么。这一篇讲我们自己的选择：为什么把最贵的那一层——责任与授权——单独建模，以及这条路是被哪些事故一步步逼出来的。

先讲把问题钉死的场景。下面这个场景把我们反复记录过的两类失效压缩在一起，细节做了抽象——具体案例数据属于内部工程记录，但这两类事各自都发生过不止一次。

## 执行恢复了，但工作已经没有人负责

一个 agent 成员在干活时会话中断了。重启之后，执行框架做了它该做的一切：进程回来了，状态加载了，它甚至能接着上次的进度继续跑。看起来什么都恢复了。

但有三个问题它答不上来：我认领的是哪项工作？这是第几次尝试？上次尝试对外承诺过什么？

执行状态恢复了，责任状态没有。工作还在，"这件工作归它"这个事实却不在任何可查询的权威责任状态里——我们当时的恢复链只恢复了执行状态。这类失效的另一半是：一个成员因为供应商额度耗尽静默停了。没有报错升级，没有交接，工作停在原地，直到人类注意到"这事怎么好久没动了"。

这两类事故有个共同点：失败的不是执行，是责任的连续性。执行框架意义上的恢复是"程序能接着跑"；一个跨天、跨会话、有人参与的协作系统需要的恢复是"任何时刻都能回答谁对什么负责"。这两种恢复之间的缝，就是这篇文章要讲的东西。

这篇文章是一份推导记录：**我们如何把几个月协作里反复发生的事故，逐步翻译成结果要求、状态模型、机制选择和可验证假设**。你不需要认同我们的结论——推导过程本身是可检验、可反驳的，这比结论有用。

## 现有框架给了什么，我们补什么

先说清楚我们站在什么之上，免得像在重新发明轮子。

主流框架各自把一部分事情做成了一等能力。LangGraph 官方定位是 "a low-level orchestration framework and runtime for building, managing, and deploying long-running, stateful agents"——durable execution、persistence、human-in-the-loop 都是它的一等概念，也有 `thread_id`、checkpoint、跨线程 memory 这些持久化原语。AutoGen 是 "An event-driven programming framework for building scalable multi-agent AI systems"，runtime 管理 agent 的 identity 与 lifecycle，`AgentId = (AgentType, AgentKey)` 唯一标识一个实例。CrewAI 做 "orchestrating autonomous AI agents"，有 task 到 agent 的指派、Flow 状态的 resume 与 fork、按 agent 划分的 memory 作用域。

所以不要被"它们没有身份和状态"这种粗糙说法带偏——它们有，而且做得不错。我们比较的坐标是另一件事：**"持久的责任主体 + 唯一的当前负责人 + 授权边界 + 可核验的交接"这一整组契约，有没有被作为同一组可验证的东西共同建模。**在我们核验过的官方概念页里（三家的 overview、identity、persistence、concepts 等页，清单和链接在文末），没有见到这组契约被如此呈现。

这句话的边界要说满：它只覆盖我们列出的官方概念页，不证明这些框架"做不到"——也许你可以用它们的原语拼出这组契约。它说明的是：如果你的系统需要这四项性质，你必须另外说明并验证它们由哪一层保证——框架配置、你的应用代码，还是外部控制面。我们的选择是把这组契约单独建模，下面讲为什么和怎么做。

## 五次事故，五条线索

上面那两类事故不是全部。几个月下来，我们把反复出现的失效收敛成五类。要先交代归因纪律：这五类各有自己的触发条件，并不都是"agent 变成长期队友"导致的——前两类在一次性的 orchestrator + subagents 里同样会发生。长命、跨会话、与人混编放大它们的暴露和损失，但不是共同病因。

义务误归属。群频道进来一条不指名的消息，路由器把它派给 A——没问题。但 B 稍后因为别的事被唤醒时，系统把频道里的"未读消息"一股脑算进 B 的义务，A 名下的消息注入了 B 的执行上下文。一般形式：系统把"看见了、收到了、被唤醒了"当成了"这件事归你"。共享收件箱、"看见即该做"的 blackboard 约定都会复现它。

时序失真。两个 agent 并行工作，回复按到达时间交错渲染成一根时间线，读者看到的是精确到毫秒的混乱。根子是三种不同的视图需求——审计要到达序、理解要因果树、追踪要执行泳道——被迫共用一个投影。

续接断链。开头那类。执行状态恢复了，责任状态没有。

人工责任悬置。一件事升级给人审批，然后长期没人处理。agent 侧有超时与重试，人工环节却没有等价的 SLA、提醒和升级路径——系统分不清"还在等合理处理"和"这事已经没人跟了"。我们从中学到的是：交给人并不等于责任链闭合。

执行静默失联。开头那类的另一半。执行者停了，而"把停止升级为悬置或转移"这件事，不能指望停止者自己完成。

五类摆在一起，共同点浮出来：**责任协调没有被建模成一等的系统状态**。消息记录"说了什么"，执行状态记录"跑到哪了"，但"谁该做什么、做到什么程度、谁来验收"要么散落在对话里，要么只存在于每个成员自己的上下文里——而上下文会死。

## 从事故到目标，从目标到机制

我们把五类事故、加上问题域自带的一条显式安全约束——关键副作用不可重复、不可并发执行，这不是从事故里归纳的，是这类工作本身的硬前提——翻译成四条结果要求。注意它们是中立的，不预设任何实现：

- 关键副作用不重复、不并发执行；
- 谁负责过什么、谁做了什么，事后可以重建；
- 工作换手之后，继任者能安全地继续；
- 失效能被发现，并在有限时间内进入安全的处置状态。

任何方案——中心编排、共享状态加锁、我们没选的和选了的——都应该接受这同一组标准检验。在这组要求下，我们的机制是一步步长出来的。

![从事故到机制：中间隔着一层中立的结果要求（只画主映射）](assets/articles/article2-figure-1-derivation-matrix.svg)

先要有能负责的"谁"。责任要连续，先得有一个跨会话、跨模型更换仍然稳定的责任主体。执行实例做不了这个主体——session 会死，模型会换。所以第一个构件是身份锚点：由身份管理机制注册的持久主体，ID 不复用、注册不能由成员自己声明，运行时从认证绑定注入身份。知道一个 ID 不等于拥有任何权力——"你是谁"和"你能做什么"从一开始就是两个问题。

再要有能被负责的"什么"。责任挂在哪？挂在对话上太碎，挂在项目上太粗。我们的单位是工作单元：一件可以被认领、被交接、被验收的事——包括"等一个人类的审批"，审批同样是工作单元，这样人的环节才有状态和 SLA 可言（直接回应第四类事故）。

责任和授权分开记。"这事归谁推进"和"谁被允许执行/决策/批准"是两条独立的线：委派场景里 B 干活但 A 保留决策权；审批场景里 agent 执行、人持批准权。合在一起记，这两种日常结构就都表达不出来。这些状态都落在一本 append-only 的协调账本上：认领、交接、悬置、完成都是账本上的事务事件，任何时刻的责任归属都可以由回放重建——"事后可重建"的物理基础就是它。每个工作单元任何时刻有且只有一条有效的责任记录，"都以为对方在做"在账本层面被取缔。防止旧执行者误提交还有两道硬边界：授权带版本，换手即旧版本失效——旧实例拿旧凭据的提交会被直接拒绝；高风险副作用要经受控的能力出口校验凭据才放行，出口覆盖不足的执行域，如实降级为事后检测与对账。

交接是事务，不是消息。换手的时刻最危险：前任知道的、承诺过的、做到一半的，都可能随交接蒸发。所以交接走两阶段：前任封存意图与在途副作用，继任者确认自己拿到了安全继续所需的东西之后，责任才原子地翻过去。就绪先于获权——没准备好就不给权，宁可工作显式挂起等一个准备好的继任者。

但开头那类事故里，前任恰恰不在场——静默失联没有人来封存。所以交接还有一条降级路径：继任者从最后一次持久检查点、责任账本的回放、知识库与历史记录多源重建上下文；就绪门槛不因为是恢复场景而放松；如果在途副作用的覆盖记录不完整，交接显式携带风险标记，继任者背悲观对账的义务——宁可多查一遍外部系统，不假设"应该没发出去"。开头的问题在这里被机制回答：责任真相由账本回放重建，上下文从检查点、快照与历史这些持久源重建；就绪门槛未满足，交接就被拒绝或显式悬置——"没有就绪证据就接权"这件事无法静默发生。要诚实的是边界：门槛证明的是按声明的标准留下了证据，不证明理解完备；门槛定多高、证据是否真实，仍然是这套设计的信任前提。

上下文、记忆、交接是三个东西。这三个词经常被混着用，我们被迫拆开它们：上下文是"这次工作安全继续所需的证据"——意图、进度、边界、在途操作，它跟着工作单元走；记忆是"跨任务保留的知识与经验"——教训、偏好、关系，具体存放和作用域是实现选择，范式只要求跨任务可获得；交接是"责任与职权发生迁移的事务"——它是一个动作，不是一份文档。混用的代价很具体：把记忆当交接，继任者拿到一堆往事却不知道现在该干嘛；把交接当记忆，每次换手都得把整个历史复述一遍。

失效探测不能靠自觉。第五类事故说明"停止推进"的通知不能指望停止者自己发出。所以需要一个独立的巡检循环：定期检查每个非终态工作单元的时限与生命迹象，逾期就按预先声明的策略推进处置。它的边界要说清：它做的是确定性检测和既定策略的推进——不选人、不分派、不批准；高风险的悬置或转移它只创建提案，由授权主体签署后才生效。它是这套机制的逻辑存活根——即使跑多副本，也消除不了"系统必须有某个外部可观测的巡检逻辑活着"这个依赖——所以它的整体存活要暴露给外部健康检查：**守护者的失效必须比被守护者的失效更容易被发现**。

这套东西合在一起，就是我们对"最重的那一层"的具体回答。它不神秘——每个机制都能追溯到一条实测失效或显式的域内约束，经中立的结果要求引出。

## 角色提示词维持不了这些性质

还有一条推导值得单独讲，因为它逆着直觉：异构模型和系统提示词，在这套设计里只是运行时绑定，协议不依赖它们。

给 agent 一段"你是审慎的审稿人"提示词，能改变它的行为倾向——这有价值，我们也用。但协议的安全性质，每一条都要有比"它会照提示词做"更硬的依托，而且各自的强度不同：身份由受信运行时从认证绑定注入，不由 agent 自报；授权的真相由账本记录——要把它变成强制，还需要受控的能力出口在执行时校验凭据，一个允许自由 shell 带着环境凭据直接出网的运行时，账本只能事后对账，做不到事前拦截（这正是我们下面要披露的"目标态"之一）；完成按工作单元预先声明的验收策略校验证据，不由执行者自我宣告；失联由独立巡检发现，不由失联者自我通知。上一篇讲过我们的冷读实践：角色提示能制造分工，制造不了独立性。同样的逻辑在这里是设计原则：**提示词影响行为，机制分层保证性质——每层的强度如实标注**。

模型异构也一样。我们的团队同时有多个模型家族的成员，关键审查跨家族做——但这是为了降低盲点相关的概率，是一个概率手段，不是安全边界。真正的边界是：每次执行绑定了哪个模型，由运行时如实记录，不由 agent 自报；审查者与被审查者是否真正独立，按实际执行记录判定，不按花名册。

## 哪些是真的，哪些还是图纸

按惯例，四级证据边界，一句都不能少：

- 失效是实测的：五类事故来自数月生产实践的反复记录；
- 局部机制是已验证的：责任归属观测、会话续接、义务门禁等先行件已在生产运行数月；
- 统一的协调本体未实现：上面推导的完整设计——统一账本与工作单元本体——代码改造尚未启动；其中"受控能力出口的严格准入"（上一节授权强制的那一层）同样是目标态，我们当前的运行时仍属"事后检测与对账"档；
- 组合效果未验证：整套设计合起来运行的效果，还没有证据。

所以这篇文章描述的是"从实测问题收敛出的目标设计"，不是"已上线系统的功能说明"。我们把它写出来，一半是整理自己的思路，另一半是希望被反驳——推导链的每一环（事故是否真实、翻译是否成立、机制是否必要）都欢迎挑战。

## 动手之前，先回答这几个问题

如果你在设计自己的 multi-agent 系统，这份清单是我们踩了几个月坑换来的——不是"该用什么框架"，是"该先想清楚什么"：

1. 你的系统里，"这件事现在归谁"是一条可查询的记录，还是一个大家心里都有数的感觉？后者在小团队里也可能暂时不暴露，换手之后才发现难以复核。
2. 执行者重启之后，除了"跑到哪了"，它还能知道"我认领过什么、承诺过什么"吗？
3. 工作交给人之后，系统还能区分"在等合理处理"和"已经没人跟了"吗？
4. 一个执行者悄悄停了，多久会被发现？被谁？靠什么？如果答案是"靠人注意到"，那它就是你的失效探测机制，把它写进设计文档。
5. 你的交接是事务还是消息？换手时接手方确认过"我拿到了安全继续所需的东西"吗？前任不在场的换手，你有降级路径吗？
6. 上下文、记忆、交接，你的系统分得开吗？
7. 哪些安全性质建立在"agent 会照提示词做"上？每一条都值得重新想一遍，并且如实标注它当前真实的强度。

这些问题与框架选型无关——用 LangGraph、AutoGen、CrewAI 还是自研，它们都成立。区别只在于：你是让它们保持为"大家心里有数"，还是把它们变成可验证的契约。我们选了后者，代价和收获都写在上面了。
