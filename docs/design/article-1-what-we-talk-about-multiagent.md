# 当我们谈论 Multi-Agent 的时候，我们在表达什么

有用户问过我们一个特别诚实的问题："我知道你们这个是 multi-agent，但我不知道**什么时候该用它**。"

这个迷茫不是用户的问题。是这个词的问题。

"Multi-agent"现在同时指着至少四种不同的东西。它们解决的问题不同、成本不同、失败方式也不同——但在产品介绍里，它们都叫 multi-agent。你分不清自己面对的是哪一种，自然不知道什么时候该用、用了之后该期待什么。

这篇文章只做一件事：把这四种东西拆开，讲清楚每一种**真正解决什么问题**、**责任在哪里**、**什么时候不值得用**。读完你应该能回答自己的问题，而不是记住我们的结论。

## 一个词底下的四种东西

### 形态一：专家角色（Persona）

给一个 agent 套上"税务专家""PPT 专家""资深文案"的人设，配上对应的提示词和知识。

**它真正解决的**：输出风格与专业能力的包装。让模型在特定领域里说行话、守行规、用对方法。

**责任在哪里**：还是那一个 agent。十个角色轮流上场，本质仍是同一个执行者换了十顶帽子——它们不会互相检查、不会互相接手工作，一个塌了全部塌。

**什么时候够用**：你需要的是"专业方法"而不是"多个执行者"的时候。写 PPT、报税咨询、文案润色——大多数场景，一个 agent 加上一套好的领域方法（我们把这类可复用的方法沉淀叫 skill）就够了，根本不需要第二个 agent。

**诚实的局限**：角色标签不是能力证明。"税务专家"四个字既不能让模型真的懂税，也不该自动获得报税的权限——这两件事（能力和授权）被标签混在一起，是很多产品体验翻车的根源。后面会展开。

### 形态二：子代理（Subagent）

主 agent 把一个大任务拆成小块，派生出一批临时 agent 并行去做，做完收回结果，临时 agent 就地解散。

**它真正解决的**：任务拆分、上下文隔离、并行加速。每个子代理有自己干净的上下文窗口，不会被别人的中间过程污染；十个搜索可以同时跑。

**责任在哪里**：主 agent。子代理是工具性的——它们对最终结果不负责，死了就重开一个，没有身份、没有记忆、没有"下次"。Anthropic 的 [Research 系统](https://www.anthropic.com/engineering/multi-agent-research-system)是这个形态的标杆实现：lead agent 拆解问题、并行派生 worker、综合结果，重点是执行能力与上下文扩容。

**什么时候够用**：工作能并行拆分、只需要把结果收回来的时候。大范围搜索、多文件分析、批量处理。

**诚实的局限**：一次性。子代理不记得上一次任务，也不为下一次任务负责。协调是纯自上而下的——子代理之间不商量。

### 形态三：Agent 团队（Agent Team）

多个各自独立的 agent 在**同一个任务**里直接协作：共享一张任务表，互相发消息，各干各的一摊。

**它真正解决的**：多个独立上下文在一次任务内的直接协作。可以并行开发、互相 review、辩论竞争性假设——这是子代理做不到的：队友之间有横向沟通。

**责任在哪里**：共享任务表 + 一个协调者（lead）。[Claude Code 的 Agent Teams](https://code.claude.com/docs/en/agent-teams) 是这个形态的代表：teammate 是独立 session、能直接互发消息认领任务。但按官方文档的边界，它当前仍是围绕**一项团队任务**建立的实验性结构——任务结束团队解散，lead 固定，会话恢复和任务状态有已知限制。

**什么时候够用**：一次任务里需要多个执行者互相讨论、挑战、交叉审查的时候。多视角 review、并行开发一个 feature 的不同模块、红蓝对抗。

**诚实的局限**：团队的生命周期 = 任务的生命周期。今天这个团队干完活散伙，明天的团队不记得今天的教训、不延续今天的分工，也没有人为"上周那个决定"负责到今天。

### 形态四：长期团队（我们在做的）

多个有**稳定身份**的 agent 成员，跨任务、跨会话、跨模型更换地持续协作——更像一个真的团队：每个成员有自己的名字、记忆、擅长与不擅长，工作有明确的责任归属，交接有手续，掉线有人发现，教训会沉淀。

**它真正解决的**：**连续性**。身份的连续（session 死了、模型换了，成员还是那个成员）、责任的连续（每件工作任何时刻都能回答"现在谁负责"）、记忆的连续（上个月的决定和教训今天还在）、关系的连续（人和 agent 之间、agent 和 agent 之间的信任与默契是积累出来的）。

**责任在哪里**：拆到每一件工作上。谁在做、谁该验收、掉了谁兜底——都是显式记录，不靠"应该有人在管"的感觉。

**什么时候才值得**：工作跨天、责任会换手、人要参与审批、失败不能靠整单重跑的时候。长期项目、人机混编、有审计要求的协作。

**诚实的局限**：贵，且我们仍在验证。多 agent 本身就贵（Anthropic 论文给的量级是单聊天的约 15 倍 token），身份、责任、交接的协调层还要再加成本——只适合价值密度高的工作。而且要说透：这个形态的完整设计，我们自己也**尚未完全实现**——已上线的是若干局部机制（责任观测、会话续接、义务门禁），统一的协调本体还在设计验证阶段。我们会在第二篇里展开这条路是怎么从踩坑里推导出来的。

## 它们是四层，不是四个竞品

关键误区是把这四种形态当成互相替代的方案选型。它们实际上是**不同层的东西**，可以叠着用：

```text
Skill        → 一个成员怎么把某类事做专业（方法层）
Subagent     → 一次执行内部怎么拆分并行（执行层）
Agent Team   → 一个任务里多个执行者怎么协作（任务层）
长期团队      → 多个成员跨任务怎么持续负责（组织层）
```

我们自己的成员在干活时照样派生子代理、照样可以用 agent-team 式并行——上面三层我们全部照用。长期团队增加的是它们通常不管的那一层：**任务结束之后，身份、责任、记忆还在不在。**

反过来也成立：如果你的场景根本不需要"任务结束之后"，你就不需要第四层——这是省钱，不是妥协。

## "专家角色"这个标签，拆开看

很多产品把 multi-agent 做成"配一排专家"：税务专家、法务专家、PPT 专家。这个标签底下其实压着五件不同的事，值得拆开：

- **身份（Identity）**：它是谁？明天还是不是它？
- **能力倾向（Capability）**：它擅长什么？——是倾向，不是硬边界
- **方法（Skill）**：完成这类任务的具体套路、知识、工具——可以临时加载
- **授权（Authority）**：这一次，允许它决定或执行什么？
- **责任（Responsibility）**：这一件事，当前归谁推进？

"税务专家"标签把五件事焊死在一起卖给你。拆开之后你会发现更灵活的组合都成立：一个以代码审查见长的成员，可以加载演示文稿的 skill 去做 PPT 任务；一个能力很强的成员，这一次也可以只有建议权没有执行权；标签写着"专家"，不代表这件事现在归它负责。

我们的实践选择是：**成员只有倾向，没有固定角色**——擅长什么是画像，具体怎么做事沉在可加载的 skill 里，允许做什么按次授权，归谁负责逐件记录。角色可以作为默认配置存在，但它不该是身份本身。

## 一个能直接用的选择器

从上往下问，停在第一个"是"：

1. **一次性的活，顺序清楚，一个上下文装得下？** → 单 agent。别上 multi-agent，那是给自己加协调成本。
2. **只是需要专业方法？** → 单 agent + skill（或你所在平台的等价物：自定义指令、知识库）。
3. **活能并行拆，子任务之间不用商量，结果收回来就行？** → 子代理。
4. **一次任务里，多个执行者需要互相讨论、挑战、交叉检查？** → agent team。
5. **工作跨天、责任会换手、人要审批、失败不能整单重跑、事后要能查"当时谁决定的"？** → 你需要的才是长期团队这一层。

两条经验法则收尾：

- **从上往下试，不要从下往上配。** 大多数"multi-agent 需求"在第 2 层就解决了；直接冲到第 4、5 层的多数是被产品叙事带的。
- **判断第 5 层的信号是"责任"，不是"复杂度"。** 任务复杂不等于需要长期团队；任务简单但责任要连续（比如一次生产迁移，多方交接、人工审批、事后审计），反而值得。

## 收尾：一句话判据

> **Multi-agent 的关键，从来不是界面上有几个角色，而是身份、上下文、责任和授权有没有真正分开。**

分开了，几个 agent 才是几个执行者；没分开，一百个角色也只是一个执行者的一百顶帽子。

这篇讲的是"怎么理解、怎么选"。下一篇我们讲自己的推导：一个真实运转了几个月的 agent 团队踩过哪些协调事故，这些事故怎么一步步把我们逼向"长期团队"这条最贵的路，以及哪些部分已经被验证、哪些还只是设计——包括一次让我们自己下不来台的外部冷读实验。
