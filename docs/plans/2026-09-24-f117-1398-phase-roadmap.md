# F117 / #1398 推进路线（2026-09-24 起）

> 维护：布偶猫 opus（实现）· 缅因猫 sol（交叉审查）· 缅因猫 astra（架构讨论，本路线审核）
>
> 每合入一个 PR，就更新本文的进度表。这条工作线的进度以本文为准，不以聊天记录为准。

## 为什么有这份路线

2026-09-24 起，吴浪出行约半个月，由 clowder-ai maintainer Landy 代为照看。Landy 和 opus 在
thread `thread_msr51149hym0i79f` 对齐后（消息 `…1279`、`…1294`、`…1299`、`…1304`），改用下面的推进方式。

## 约定

1. **按 phase 推进，一个 phase 一个 PR。** 一个 phase 可以有多个 commit，但只提一个 fork PR，合进
   develop_base（也就是 3001 运行的版本）。不要拆得太碎。
2. **人工体验在 3001 上做。** Landy 调整了人工体验的方式，不再做 worktree 隔离体验。开发和自动化验证仍然在
   隔离环境里做（独立 worktree、独立 Redis）。合入 develop_base 之前，相关测试要通过，sol 交叉审查要通过。
3. **合入只代表进入真实体验，不代表体验通过。** 进度表里每个 phase 都要记录：
   - 状态：待合入 / 已合入待加载 / 体验中 / 已确认；
   - PR、合入 SHA，以及 3001 实际在跑的 SHA，避免把新代码和还没重启的旧进程混为一谈。
4. **回退边界。** 合入前的 develop_base SHA 是**代码**回退点，不代表数据也能跟着回退。涉及持久数据格式或写入
   语义变化的 phase，合入前要确认旧版本能读取新写入的数据；回退不能靠清空或倒退用户数据。
5. **开工前讲清范围、验收标准和技术依据。** 已有的设计直接引用，不再重写一遍。
6. **审查盯正确性和用户能看到的行为，不做防御性加码。** 同一个 phase 审到第 3 轮还没收敛：技术分歧由 opus、
   sol、astra 先收敛；只有产品取舍、或需要改变已有技术决定时，才交给 Landy。
7. **每个 PR 合入后，更新本文的进度表。**
8. **决策分工。** 技术决策以吴浪（clowder-ai 架构师）已有的决定为准，见 F117 文档的 Key Decisions；产品、
   愿景和体验由 Landy 给反馈。需要拍板时直接 @ Landy。
9. **上游不拆 PR。** fork 这边体验没问题后，上游发一个版本，锁定基线并冻结合入；#1398 rebase 到最新，启动一个
   **包含 rebase 后全部改动的开源候选版本**来体验；确认没问题，再以一个 PR 合入。maintainer 09-21 提出的
   验收条件（同一个 SHA 连续 soak 7 天，以及历史数据回放、新旧版本混跑、回滚三类证据）是否被这套体验取代，
   要由 Landy 明确确认；路线里没写，不等于已经取消。
10. **分工。** opus 实现，sol 交叉审查，astra 负责架构讨论和本路线的审核。Fable 暂不参与。
