## 为什么有这份路线

## 约定

1. **按 phase 推进，一个 phase 一个 PR。** 一个 phase 可以有多个 commit，但只提一个 fork PR，合进
   develop_base（也就是 3001 运行的版本）。不要拆得太碎。
2. **人工体验在 3001 上做。** Landy 调整了人工体验的方式，不再做 worktree 隔离体验。开发和自动化验证仍然在
   隔离环境里做（独立 worktree、独立 Redis）。合入 develop_base 之前，相关测试要通过，运行实例自己的构建也要
   通过（shared、MCP、API 的构建和前端 `next build`，与 3001 重启时执行的一致），交叉审查要通过。
3. **合入只代表进入真实体验，不代表体验通过。** 进度表里每个 phase 都要记录：
   - 状态：待合入 / 已合入待加载 / 体验中 / 已确认；
   - PR、合入 SHA，以及 3001 实际在跑的 SHA，避免把新代码和还没重启的旧进程混为一谈。
4. **回退边界。** 合入前的 develop_base SHA 是**代码**回退点，不代表数据也能跟着回退。涉及持久数据格式或写入
   语义变化的 phase，合入前要确认旧版本能读取新写入的数据；回退不能靠清空或倒退用户数据。
5. **开工前讲清范围、验收标准和技术依据。** 已有的设计直接引用，不再重写一遍。
6. **审查盯正确性和用户能看到的行为，不做防御性加码。** 同一个 phase 审到第 3 轮还没收敛：技术分歧由 opus 和
   审查者先收敛，大的架构取舍拉上 Fable；只有产品取舍、或需要改变已有技术决定时，才交给 Landy。
7. **每个 PR 合入后，更新本文的进度表。**
8. **决策分工。** 技术决策以吴浪（clowder-ai 架构师）已有的决定为准，见 F117 文档的 Key Decisions；产品、
   愿景和体验由 Landy 给反馈。需要拍板时直接 @ Landy。
9. **上游不拆 PR。** fork 这边体验没问题后，上游发一个版本，锁定基线并冻结合入；#1398 rebase 到最新，启动一个
   **包含 rebase 后全部改动的开源候选版本**来体验；确认没问题，再以一个 PR 合入。maintainer 09-21 提出的
   验收条件（同一个 SHA 连续 soak 7 天，以及历史数据回放、新旧版本混跑、回滚三类证据）是否被这套体验取代，
   要由 Landy 明确确认；路线里没写，不等于已经取消。
10. **分工。** opus 实现，kimi 交叉审查；遇到架构上的大取舍，找 Fable 商量（Landy 09-25 调整，`…000100`：sol、astra

11. **交给 Landy 体验之前，先在 alpha 自测。** 能用浏览器验的特性，开发完后在 alpha（`scripts/alpha-worktree.sh`，
    3011/3012，独立 Redis）里用浏览器自己验一遍；发现问题先修，再合入、交给 Landy 在 3001 体验（Landy 09-27，`…000735`）。
    alpha 验收默认派给 sol：他的额度多，家里也好有协作（`…000742`；本地缅因猫额度 09-27 已恢复，`…000468`）。Phase 4 由
    opus 自己验。alpha 的 Redis 不能用运行实例的数据目录：以前脚本只覆盖端口和 `REDIS_URL`，继承来的 `REDIS_DATA_DIR`、

    不动配置和未跟踪文件，不重启。然后再请 Landy 择时重启。进度表里的「3001 运行 SHA」以运行目录的 HEAD 和重启时间为准。
    本文和其他共享状态文档直接在运行目录改并推送（shared-rules §14），避免运行目录里的副本落后。

**B. 流式输出时 React 报「Maximum update depth exceeded」（要先复现才能定根因）**
- 现象：两路同时流式输出（opus SDK 和 codex app-server）时，控制台报了两次，页面仍然能用（记录「Provisioned-alpha continuation」）。
- 已知：这是 #789 那类问题的复发。#953 的缓解办法是 coalescer 每个微任务最多处理 6 个事件，前提假设是每个事件最多 8 次
  zustand `set()`。这次抛错的位置是 coalescer 刷新 → `handleActiveText` → `setCatInvocation`。F117 的重构（`f8071e44a`）
  改写了这条路径。现在每个文本块有 4 次无条件的 `set()`：`setLastSeq`、追加正文、活动时间，以及每块都会生成新对象的
  `setCatInvocation({ livenessWarning: undefined })`。文本块带元数据或执行身份时，再多 1～2 次。`setCatStatus` 值没变时不通知订阅者。
- 还没确定：按 #953 的模型，6 个事件大约是 24～36 次，本不该超过 50，所以光看 `set()` 次数解释不了这次复发。React 只在
  连续 50 次以上的提交结束时都还留着同步更新，才抛这个错；抛错的地方只是最后一次调用，不一定是循环本身。#953 那套
  「按 `set()` 次数计算」的模型也从没用真实渲染验证过，现有的 burst 测试只数了通知次数。所以更可能是某个组件在提交时
  反复排同步更新，但要复现才能定。
- 影响：错误会一路冒出 zustand 的通知循环，造成两处缺失：
  - 这一块文本不会写进气泡；
  - coalescer 这一批剩下的事件（最多 5 个）已经出队，会被直接丢掉。

  丢掉的事件能被 F183 的序号缺口补拉兜住，最终又以提交的 R 为准，所以这是暂时的显示缺失，不是数据丢失。生产构建里同样会抛
  （React #185）。
- 修复范围（先复现再修，都在 web 包里，属于 F117 这条线）：
  1. 复现：用真实的 chatStore 和消息列表做一个 jsdom 渲染测试，把两路交错的流式事件送进 coalescer，断言不出这个错。
     jsdom 复现不了的话，就在 alpha 里用浏览器挂 React 的提交钩子，记下是哪个组件每次提交都留下同步更新。
  2. 按复现结果修：
     - 如果是某个组件在提交时反复回写：修那个组件，这是根因修复；
     - 如果确实是 `set()` 太多：让每个文本事件只提交一次 store 更新（合并成一次 `set()`，值没变的更新直接跳过，比如
       `livenessWarning` 本来就是空的时候）。

     不论是哪种，都让 coalescer 在单个事件出错时不丢同批的其余事件：这是缩小影响，不能替代根因修复。
  3. 回归测试：用真实渲染做突发流式测试，防止预算以后又悄悄超出。
