### 怎么迁（三条原则）

1. 插件的业务逻辑**整体搬走、不重写**。
2. 只改「和 Host 打交道的那一圈」：Host 把这一圈做成通用接口；插件仓让 SDK 包住它，插件改用 SDK。
3. Host 为某一个插件单独写的接口 / 卡片 / 工具 / 管理，一律收敛到通用机制，不原样搬。
4. **「整体搬走、没改」要可验证**（operator 09-21：风险只在插件与 Host 之间的桥；搬过去的逻辑没改，上游 review 只需看边界）。
   跨仓搬迁在 diff 里是一边删、一边增，reviewer 看不出「没改」，所以：搬迁与边缘改动分开提交（先纯搬、后改边缘）；附一份机械对照——
   逐文件比对 Host 删掉的与插件仓新增的，列出全部差异行，它们应当恰好等于「只改的边缘」那一列。PR 描述里写明：核心改动 = Host 补的接口 + 这份差异清单。

### 顺序与完成标准（同一个 PR，不留 followup）

1. Host 做 A–E → commit。2. 通知插件仓做 a–e。3. Host 逐包做 F、G，按由易到难的波次：① 视频、微信公众号、微信会话读取、enterprise workflow → ② 7 个 connector 与 ChatGPT Pro（同一条消息链路）→ ③ github 整簇 → ④ collective、GenOffice 的 docx 生成 → 飞书纪要同步随插件仓改造完成时删。每一波都是：装包 → 跑通 → 确认不双跑 → 删，分支始终可用。4. 收尾 I（自动安装内置插件），并由 operator 定 H（已有数据迁移还是忽略）。5. 插件仓发布 contract / SDK → Host pin → worktree 验收。

**验收不等 npm 发布**（operator 09-21）：每一波的「装包」用插件仓**本地打出来的包**即可——Host 的插件管理本来就支持本地目录、本地压缩包和上传安装
（`PluginManagerPackageSource` 的 `local-directory` / `local-archive`，`/api/plugin-manager/plugins/install/upload`）；两仓迁移清单的依赖顺序也是「先打包产物、后发布」。
唯一例外是 **contract 包**：Host 在构建期依赖它（`packages/api/package.json:62`），开发期可以用本地 tarball，但 Host 这个 PR 合入上游之前必须换成已发布的版本号。

**完成标准**：上表各项从安装包装上并能用（ChatGPT Pro 为「与现状一致」）；Host 与 SDK / contract 里只为某个插件服务的后端代码、接口、路由删净；留下的只有 C2 表里那些定制前端。
规模估计：Host 生产代码新增仍是 3 千行上下（测试另计）；离开 Host 的约 4.6 万行，是上一版估计的两倍；前端改动另计。

**风险（按严重程度）**：① 会动到用户数据的归属——社区看板数据、collective 的配对密钥（`~/.cat-cafe/collective-service/`）、connector 绑定与配置、会议 intake；一律「只复制不删除」的迁移脚本，由 operator 择时执行，任何删除都要 operator 明确授权。② tracking、社区运营工具是我们每只猫每天在用的工作流，搬坏先伤自己——逐项不双跑开关 + 「先禁用包、再恢复 Host 实现」的回滚路径。③ 一个 PR 约 4.6 万行删除，上游 maintainer 的 review 负担很重。④ collective、社区看板、GenOffice docx 生成三项只做了依赖扫描（社区看板 9,059 行对 Host 的依赖集中在 cats 域的存储，20 个 Host 文件反向依赖它），**没有逐处核调用**，轮到它们之前要先核完。

## 执行账本——怎么干、干成什么样、现在到哪了

> operator 09-21：「怎么干、干成怎么样记得刷新到文档，免得干到一半又跑偏。」
> **规矩**：一次只放一片；每片先红后绿；实现的猫（sol）推送后交 reviewer（宪宪 / Fable）；reviewer 逐条对照「干成什么样」与下面的防跑偏线，
> 通过后**由 reviewer 更新本表状态并写上 commit**，再放下一片。thread 里的口头任务不算数，以本表为准。发现本表与代码冲突：带 file:line 退回，不自己换方向。
> **毛线球在交回时就关（2026-09-21 改）**：实现方推送之后先把当轮毛线球标 done、再 @ reviewer——「实现完成」就是 implement 租约的终点 `task_done`，也是交回时唯一一定可用的可验证状态迁移；毛线球 done ≠ 本片通过，本片状态只看本表。复审不过，由 reviewer 另建返工毛线球再派。原先「等复审通过再关」的做法作废：它让实现方交回时拿不出任何结构化出口，F167 停止门随即停掉 thread 的猫间接力，之后回给实现方的消息被静默取消，当天停摆两次、都靠 operator 发话才恢复。

### 防跑偏线（每一片都适用，任何一条破了就退回）

1. 不新造抽象：能用 main 现成原语的就薄包它（`addSkill` / `removeSkill`、mcp 安装、`limbRegistry`、`taskRunner`、`messageStore`、`threadStore`、`taskStore`）。
2. Host 不 import SDK；给插件的形状由 Host 结构化定义（同 `PluginModuleEntrypointShape` 的做法）。
3. Host 里不出现任何插件 id、平台名、`github` / `feishu` 之类的分支；不为单个插件写接口、路由、卡片、工具。
