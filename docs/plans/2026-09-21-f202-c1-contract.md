## 0. 准绳（operator 原话，thread `thread_mu8dg6h7l2x4ohsk`）

1. **通用能力，不留专属接口。**「host 使用已有的 增删改查 thread / 历史 message / 发送消息 / 注册监听回调的消息
   之类的这些接口；然后 sdk 做这些接口的抽象封装；我们不 care 那个插件是 im connector 还是什么」
   「我们不应该留下任何定制的专属接口和能力」（09-20，`…003427`、`…003432`）
2. **两个入口汇聚。**「前端→send message 接口；插件→sdk 的 send_message 接口；这两个 send 汇聚到一个接口；
   然后开始处理和 dispatch」（`…003406`）
3. **Host→插件是一个机制。**「插件调用 host 注册声明需要订阅哪个 thread 的消息……调用插件实现的这个 outbound
   接口；插件……按照自己的逻辑处理……都是插件内部闭环的」「如果其他的插件也涉及到 host 主动调用插件的应该也是
   这个思路」（`…003444`、`…003461`）
4. **声明与交互互补。**「plugin.yaml 插件的元数据和能力声明；sdk 让插件能和 host 主动双向交互」；配置、
   connector 的 action、test 都基于 yaml 声明（09-21，`…004103`、`…004112`）
5. **分工与终态。** Host 只做两件事：补齐并收敛契约接口、提供通用插件管理。属于插件的整体搬迁、不重写；插件怎么接
   SDK 是插件仓的事。先定 Host 接口 → SDK 包装 → 插件实现；Host 不依赖 SDK。**一个 PR 做到终态**（C2 前端除外）：
   Host 里插件 / connector 代码一行不剩，插件仓的插件能独立安装、卸载、使用（`…003933`、`…004200`、`…003406`）

## 6. 我做的判断（你可以否决）与没核的

**判断**：github 的 tracking 注册（`register_pr_tracking` 写进 TaskStore 的任务）留在 Host，插件经 P7 读写——依据是
两仓迁移清单 `inventory.json` 里 github 一项写的「tracking registrations stay Host-owned」。如果你要 tracking 也
变成 github 插件自己的数据，P7 取消，`register-pr-tracking` 等三个回调随插件走。Host 自己的功能（F168 社区、
F280 等待、F208 蒸馏）留在 Host，经 P8 接收事实；community-reconciler 同此处理。

**没核的**：
- 全部来自读代码与 grep 计数，**没有跑任何构建或测试**；调用计数按对象名匹配，别名调用可能有漏。

  是否与前端路径汇聚，需要读完两边才能下结论。
- `connector-gateway-bootstrap.ts`（27 处）、`connector-hub.ts`（15 处）的 provider 字面量，读了分布和注释，没有逐处确认。
- 插件仓只读了提交态 `81aeb95`；工作区有未解决冲突（operator 手动暂停），没有动。
